# PR-33: explicit one-hash transaction evidence pilot

The network page offers a closed-by-default, read-only lookup of one 32-byte hexadecimal transaction hash (optional lowercase 0x prefix). Before submission it states the two fixed Midgard providers that receive the hash and network request. No arbitrary URL, account, signing, send action, stored hash/address history, automatic submit, polling or recovery promise is added. Input edits, Clear and unmount abort the prior read; an older response cannot revive cleared evidence.

The lookup requests `/actions?txid=<hash>&limit=5` using existing bounded JSON and five-second request/body deadlines, then a single fixed fallback on unusable evidence. Cancellation prevents fallback. Records must relate to the queried hash. Five actions, eight transfers/coins/fees per list and bounded text remain visible with omission/partial warnings. Addresses are not retained in the normalized model. Missing lists, malformed exact amounts, empty indexed results and unavailable providers remain distinct; valid zero and large integer strings survive. Returned source URLs and local check receipts identify the actual read.

## Incremental review and regression fixes

A read-only independent review of the published candidate found two range/omission issues. Int64 overflow could be interpreted as a date or height, and over-limit memo/reason/ID fields could be presented as absent. A failing regression reproduced these cases. Interpretation now requires the nonnegative Int64 subset of the provider contract; bounded raw date/height strings remain available with warnings. Supplied text omitted by pilot limits is explicitly reported. Exact valid zero and large in-range amounts remain preserved.

The initial Linux CI run failed the mobile Enter submission after correcting an invalid hash. A separate native-autofill regression reproduced a stale framework value. Submission now reads the visible named field through FormData; the uncontrolled native field survives parent refreshes. The original Enter-key check remains in place. No additional lookup is triggered by typing or autofill.

The freshness fixture now waits for the browser's pinned Mimir evidence before saving the receipt, rather than racing the server seed. Browser revalidation uses a one-block lag in both runtimes; the Worker's server seed retains its separate ten-block policy. Offline receipt preservation, resume aging and explicit recovery assertions are unchanged.
